\section*{Why we asked}

I ran every Claude session from my notes vault, \name{md-Wiki/}. Projects were split between \name{md-Wiki/} and a second repo nested inside it, there was no list of my projects, and after a few months Claude's memory for \name{md-Wiki/} held 147 entries: mail rules next to LaTeX rules next to how to talk to me. I no longer knew where anything was, or which project needed me.

Over two evenings we agreed on a way of working, and changed the setup to match it. This lesson is that agreement, and the evidence each part rests on.

Names follow one convention: a folder ends in \name{/}, and a link is grey and underlined; a link to a folder does both, as in \name{\home/\lk{PARA}/}. In a listing, \texttt{ls -F} marks them the same way, a folder with \texttt{/} and a link with \texttt{\symbol{64}}.

\section{Where Claude keeps what it knows}

Claude Code carries knowledge between sessions in two ways~\cite{memory}:

\begin{itemize}[leftmargin=1.2em]
  \item \textbf{instruction files} I write: \name{CLAUDE.md} files and rule files, loaded at the start of a session;
  \item \textbf{auto memory}, notes Claude writes itself when I correct it, one file per memory plus an index, \name{MEMORY.md}.
\end{itemize}

\begin{insight}{Which files load}
\name{\home/.claude/CLAUDE.md} and every file in \name{\home/.claude/rules/} load in every session, wherever it starts. A \name{CLAUDE.md} in the folder where the session starts, or above it, loads too. A \name{CLAUDE.md} further down, inside a repo, loads only once Claude reads or edits a file there. A rule file can list file patterns under the field \texttt{paths:} in its header; then it loads only when Claude touches a matching file~\cite{memory}.
\end{insight}

The docs also say where auto memory goes, and that sentence turned out to matter:

\begin{quote}
The \texttt{<project>} path is derived from the git repository, so all worktrees and subdirectories within the same repo share one auto memory directory. Outside a git repo, the project root is used instead.~\cite[\textit{Storage location}]{memory}
\end{quote}

Memory follows the \emph{git repo} the session starts in. The session transcripts, instead, are filed by the folder itself.

\section{The problem: every project shared one memory}

My plan was one folder per project, \name{\home/\lk{PARA}/Projects/<name>/}, each with its own memory. But \name{\home/\lk{PARA}/} was a link into my dotfiles, \name{\home/.settings/}, which is a git repo. If the docs were right, every project folder wrote into the dotfiles' memory.

\subsection*{Which folder did each memory come from?}

Each memory file records the session that wrote it, and each session's transcript sits in a folder named after where it ran. So I matched the two. The search is one pipeline; here it is built one stage at a time, each stage feeding the next, so every piece can be run and seen on its own. All three run in \name{\home/\lk{.claude}/projects/}, where Claude Code keeps one folder per place a session started, named after its path with every \name{/} and \name{.} turned into \name{-}; in it are that place's transcripts and its \name{memory/}. The dotfiles' memory is \name{-Users-atcold--settings/memory/}.

The memory files name their session in a header line. \name{grep} prints each matching line after the name of its file; \texttt{-h} leaves the file name out:

\begin{pane}
$ cd ~/.claude/projects
$ grep -h 'originSessionId' -- -Users-atcold--settings/memory/*.md   # one line per memory
\end{pane}
\begin{cmdout}
  originSessionId: bbedde46-fc2a-4ad9-8a6d-abd6cd9654f7
  originSessionId: aca99ffc-815a-4532-94e6-944f7aa9ab86
  …
\end{cmdout}

The \texttt{--} tells \name{grep} that what follows is a file: without it, \name{grep} would read \name{-Users-atcold--settings/…}, which starts with a dash, as a list of options, \texttt{-U}, \texttt{-s}, \texttt{-e}, and so on. \name{awk} keeps the second word of each line, the session ID, and \texttt{sort -u} drops repeats, since one session can write several memories:

\begin{pane}
$ grep -h 'originSessionId' -- -Users-atcold--settings/memory/*.md |
  awk '{print $2}' | sort -u   # each session once
\end{pane}
\begin{cmdout}
3c1706f0-cc17-4648-8c8e-c0706eda2912
aca99ffc-815a-4532-94e6-944f7aa9ab86
bbedde46-fc2a-4ad9-8a6d-abd6cd9654f7
c39c5e2f-7a56-4533-b89f-99da7d718fb4
cc218fd6-30ca-4fcb-84cf-cebdb6577842
\end{cmdout}

Last, \texttt{while read s} takes one ID per line, and \name{find} looks for that session's transcript, \name{<ID>.jsonl}, at most two folders down:

\begin{pane}
$ grep -h 'originSessionId' -- -Users-atcold--settings/memory/*.md |
  awk '{print $2}' | sort -u |
  while read s; do find . -maxdepth 2 -name "$s.jsonl"; done   # where each session ran
\end{pane}
\begin{cmdout}
./-Users-…-settings-Mac-PARA-Projects-|!altair-8800-tang-nano-9k!|/0ca59df2-….jsonl
./-Users-…-settings-Mac-PARA-Projects-|!altair-8800-tang-nano-9k!|/0f80ec61-….jsonl
./-Users-…-settings-Mac-PARA-Projects-|!xdg-base-dirs!|/5df9ced5-….jsonl
./-Users-…-settings-Mac-PARA-Projects-|!altair-8800-tang-nano-9k!|/71d9eb7c-….jsonl
\end{cmdout}

That output is from before the move.

Sessions I started in the \name{altair-8800-tang-nano-9k/} and \name{xdg-base-dirs/} project folders had written their memories, such as ‘every step goes in the worksheet’, into the dotfiles' memory. The per-project folders existed, but only for transcripts: none had a \name{memory/} inside.

\section{The fix: \name{PARA/} moves out of the repo, into Dropbox}

\name{PARA/} is only a tree of links, so it needs no \name{git}: it needs to reach both Macs. Dropbox would do, if it carries a link as a link and does not copy what the link points to.

\subsection*{Does Dropbox sync a link unchanged?}

A link already lived in Dropbox: \name{tg-mail}'s \name{\lk{accounts}/}, pointing into \name{md-Wiki/}. I looked at it from the other Mac:

\begin{pane}
$ ssh alfmac4 '/bin/ls -lF ~/Dropbox/Apps/tg-mail/ | grep accounts'   # the office Mac's copy
\end{pane}
\begin{cmdout}
lrwxr-xr-x@  1 atcold  staff      |!41!| 25 Oct 21:16 accounts@ -> /Users/atcold/md-Wiki/Areas/Mail/accounts
\end{cmdout}

Same date, same target, 41 bytes: the link itself, not the folder behind it. So \name{PARA/} moved to \name{\home/Dropbox/Apps/PARA/}, outside any repo, and \name{\home/\lk{PARA}/} points there on both Macs. Each project folder now gets its own memory, and a change to the tree needs no commit.

\name{\home/Dropbox/Apps/} holds every folder the apps and the Macs sync: \name{PARA/}, \name{claude/} (where \name{\home/\lk{.claude}/} points), \name{tg-mail/}, \name{chinese-lab/}, \name{eink/}.

\section{The agreement}

\begin{result}{How I work}
\begin{enumerate}[leftmargin=1.4em]
  \item \textbf{One project, one home.} I start Claude in \name{\home/\lk{PARA}/Projects/<name>/}, and only there for that project. Its memory lives there. The folder holds links, among them \name{\lk{repo}/} to the project's git repo in \name{\home/Work/GitHub/}.
  \item \textbf{The book is its own home:} \name{\home/\lk{Book}/}, a link to its repo, \name{\home/Work/GitHub/Book/}, as it always was.
  \item \textbf{\name{md-Wiki/} is for my areas and what spans projects:} mail (\texttt{/triage}, \texttt{/follow-up}, \texttt{/reply}), \texttt{/chinese-lesson}, the Inbox, planning, the notes themselves. Here I \emph{use} my tools; developing one is a project. Reading my mail with \name{tg-mail} happens in \name{md-Wiki/}; changing \name{tg-mail} itself happens in \name{\home/\lk{PARA}/Projects/tg-mail/}.
  \item \textbf{Rules that hold everywhere live in \name{\home/\lk{.claude}/rules/}}, one file per topic, each rule in one place.
  \item \textbf{No repo without a project.} A repo is one part of a project, next to its note, \name{\lk{local}/} for what is not version-controlled, and, for courses, \name{\lk{g-drive}/}.
\end{enumerate}
\end{result}

\name{\home/\lk{PARA}/Projects/<name>/} is a folder of links:

\begin{itemize}[leftmargin=1.2em]
  \item \textbf{\name{\lk{note.md}}}: the project's note in \name{md-Wiki/}, where the plan and the log live;
  \item \textbf{\name{\lk{repo}/}}: the git repo; with more than one, \name{\lk{repo-<x>}/} for each (the salsa manual has \name{\lk{repo}/} and \name{\lk{repo-notes}/});
  \item \textbf{\name{\lk{local}/}}: the project's data, usually a folder in Dropbox, so both Macs have it;
  \item \textbf{\name{\lk{g-drive}/}}: a Google Drive folder, to share the material with the students;
  \item \textbf{\name{\lk{lesson}/}}: a lesson in this repo, when the project's write-up is one (the printer, XDG).
\end{itemize}

Every project is listed, by area, in \name{md-Wiki/Projects/projects.md}.

\section{Experiments in the terminal}

Claude teaches me how something works by running it on my own machine, in a \name{tmux} pane, one of the panels a terminal window is split into, while I watch. This experiment comes from the session that set the habit up.

\begin{tcolorbox}[enhanced, breakable, colback=white, opacityback=1, colframe=black!40, boxrule=0.5pt, arc=1pt, title={Why softargmax subtracts the maximum}, colbacktitle=black!6, coltitle=black, fonttitle=\small\bfseries]
The softargmax function converts scores into positive weights that sum to one: it exponentiates each score, then divides by the sum of those exponentials. Subtracting the largest score before exponentiating gives the same weights while avoiding overflow.


\begingroup
\renewcommand{\panetitle}{\name{IPython} on \name{AlfMAC4}}
\begin{pane}
In [1]: x = array([88., 89.], dtype=float32)  # 32-bit scores
In [2]: e = exp(x)  # second exponential overflows
|!<ipython-input-2-71fc9e84a04c>:1: RuntimeWarning: overflow encountered in exp!|
  e = exp(x)  # second exponential overflows
In [3]: e  # finite value and infinity
|~Out[3]: array([1.6516363e+38,           inf], dtype=float32)~|
In [4]: e / e.sum()  # finite / inf and inf / inf
|!<ipython-input-4-d9dcc5de4527>:1: RuntimeWarning: invalid value encountered in divide!|
  e / e.sum()  # finite / inf and inf / inf
|~Out[4]: array([ 0., nan], dtype=float32)~|
In [5]: e = exp(x - x.max())  # shift scores to -1 and 0
In [6]: e  # exponentials fit
|~Out[6]: array([0.36787945, 1.        ], dtype=float32)~|
In [7]: e / e.sum()  # weights sum to one
|~Out[7]: array([0.26894143, 0.7310586 ], dtype=float32)~|
\end{pane}
\endgroup

The \texttt{dtype} argument chooses the array's number format. Here \texttt{float32} uses 32 bits per number, with a largest finite value of about $3.4\times10^{38}$. The smallest integer whose exponential exceeds that limit is 89: $\exp(88)\simeq1.65\times10^{38}$ fits, while $\exp(89)\simeq4.49\times10^{38}$ overflows, so the second exponential becomes \texttt{inf}. Their sum is then infinite: dividing the finite first exponential by it gives zero, while dividing infinity by infinity gives \texttt{nan}, meaning not a number. Without an explicit \texttt{dtype}, this array of decimal values uses \texttt{float64}, whose largest finite value is about $1.8\times10^{308}$: $\exp(89)$ fits, but $\exp(710)$ overflows~\cite{numpytypes}. Subtracting the largest score makes the largest exponential one and preserves the normalised weights, because the common factor cancels in the division.

\end{tcolorbox}

Each command ends with a short comment saying what it shows, so the explanation sits beside the code and its output, and the chat only reports what the experiment found. The experiment uses the tool’s own interactive session: the shell, \name{ipython}, or the equivalent for that language. The session stays open at the end, so I can carry on from there. On another machine, Claude opens \texttt{ssh} in the pane and continues there. A change to my terminal setup is tested the same way, in front of me.

The same pane works as a blackboard. Output I should look at, such as \texttt{git s} or \texttt{git lg -5}, goes there instead of into the chat, because the pane keeps its colour and layout.

These rules are in \name{terminal.md}. Because an experiment depends on which machine it runs on, a session-start hook, a command Claude Code runs at launch, adds the machine’s name to every session.

\section{Using Codex with the same project home}

\name{Codex} is OpenAI's coding assistant. I start it in the same \name{PARA} project home as \name{Claude Code}, so both work from the same project note, repository, rules, and relevant memories. Both Macs share application state through Dropbox. The versioned instructions and rules live in each Mac’s local checkout of \name{Unix-dot-files}, reached through \name{\home/.settings/}. The application homes link to these locations:

\begin{itemize}[leftmargin=1.2em]
  \item \name{\home/Dropbox/Apps/claude/}, reached through \name{\home/\lk{.claude}/}, contains:
    \begin{itemize}[leftmargin=1.2em]
      \item \name{\lk{CLAUDE.md}}, a link to \name{\home/.settings/Claude/CLAUDE.md}, and \name{\lk{rules}/}, one folder link to \name{\home/.settings/Claude/rules/};
      \item \name{skills/}, the existing task instructions;
      \item \name{projects/}, the conversations and project memories saved by \name{Claude Code}.
    \end{itemize}
  \item \name{\home/Dropbox/Apps/codex/}, reached through \name{\home/\lk{.codex}/}, contains:
    \begin{itemize}[leftmargin=1.2em]
      \item \name{\lk{AGENTS.md}}, a link to \name{\home/.settings/Codex/AGENTS.md}, which tells \name{Codex} how to use the existing Claude workflow;
      \item \name{config.toml}, the Codex settings;
      \item \name{sessions/}, the saved conversations, and supporting databases beside it;
      \item \name{skills/} and \name{plugins/}, Codex's task instructions and optional integrations, plus its authentication and runtime state in other files.
    \end{itemize}
\end{itemize}

The two folders in \name{.settings/} each have their own Bash \name{install.sh}. The Claude installer links its global instructions, the entire rules folder, and the status-line script; it uses \name{jq} to update the status-line field in the existing JSON settings. The Codex installer links its \name{AGENTS.md}. Both preserve replaced files in Scratch. Installation is described in their respective READMEs.

Each Mac needs the same settings revision: pulling the repository updates its local instruction sources, while Dropbox shares conversations and runtime state. The repository holds curated configuration examples; live JSON settings, credentials, and conversations stay in the application homes.

\subsection{How Codex reads the existing instructions}

\name{Codex} reads \name{AGENTS.md} as its instruction file. We wrote this small file to direct it to Claude's original instructions. Its opening paragraph reads:


\begin{quote}
\raggedright\small\ttfamily
Before working, read \textasciitilde{}/.claude/CLAUDE.md and the existing talking.md, writing.md, git.md, files.md, and terminal.md in \textasciitilde{}/.claude/rules/. Read latex.md there when working with .tex, .sty, or .bib files. These files are the source of truth; interpret references to Claude as applying to this assistant too. Number questions only, as the user clarified.
\end{quote}

The rest directs \name{Codex} to the PARA project home, its \name{note.md}, applicable \name{CLAUDE.md} files, and the project's existing memory index. This file is the \emph{adapter}: it tells one assistant where the other assistant's existing instructions live. The rules themselves stay in the Claude files.

\name{Codex} looks for shared skills in \name{\home/.agents/skills/}. In our setup, \name{\home/.agents/\lk{skills}/} points to \name{\home/\lk{.claude}/skills/}, so both assistants read the same skill files. The \name{.agents/} folder provides that discovery location, while \name{\lk{.codex}/} reaches Codex\textquotesingle s own settings and state. These names are application conventions rather than XDG defaults; we keep them as the paths the applications expect. The local \name{codex-ui} program and build artifacts follow XDG, as described below. These commands print the stored targets of the three links:

\begin{pane}
$ readlink ~/.codex           # Codex home
$ readlink ~/.claude          # Claude home
$ readlink ~/.agents/skills   # shared Claude skills
\end{pane}
\begin{cmdout}
Dropbox/Apps/codex
Dropbox/Apps/claude
../.claude/skills
\end{cmdout}

In \name{config.toml}, \nolinkurl{project_doc_fallback_filenames} lists \name{CLAUDE.md} as an additional project instruction filename. Another setting disables automatic external-agent imports. Such an import converts configuration from another assistant into separate Codex copies; our setup reads the originals through the adapter and skill link.

\begin{insight}{Skills and plugins}
A skill is a file of instructions for a task. A plugin packages extra capabilities, such as skills or connections to tools. For example, the PDF plugin supplies instructions for reading, creating, and checking PDF files with the available tools. For document formats covered by both libraries, our adapter tells \name{Codex} to use its native skill with the available Codex tools. It uses the shared Claude skills for the remaining tasks. The original Claude rules apply in either case.
\end{insight}

\subsection{Conversations and project progress}

\name{Claude Code} saves each project's conversation files under \name{\home/\lk{.claude}/projects/<encoded-project-path>/}. Its \name{memory/} subdirectory holds the project memories, which our \name{Codex} adapter also reads. \name{Codex} saves its conversations under \name{\home/\lk{.codex}/sessions/YYYY/MM/DD/}, with supporting databases in the shared Codex home. The PARA project's \name{note.md} carries durable progress and the next action for either assistant.

\subsection{What goes into the opening context}

\begin{insight}{What loads into the conversation}
The sentence typed into the composer is only part of what the assistant receives. \name{Codex} also receives its operating instructions, available tools, a catalogue of skill names and descriptions, and the project's instruction chain. Our adapter then asks it to read the Claude rules and project context. File contents returned by those reads become part of the conversation.

\end{insight}

A listed skill's full body is read when the task calls for it. The project note, memory, and repository files add their own text when read.

The reported 3\% after the opening prompt therefore describes accumulated context, including setup and any work already performed. It cannot be attributed to that prompt alone. This audit measures the files under our control; it does not reconstruct the exact percentage shown at that earlier moment. Context occupancy and the five-hour account allowance are separate quantities.

\subsection{The commands at the opening screen}

The suggested commands are a menu of controls, much like menu items in a desktop app. I can begin with an ordinary request. The commands below are described in the official OpenAI documentation~\cite{codexcommands} and checked against the pinned \name{Codex} source used by the custom interface.

\begin{itemize}[leftmargin=1.2em]
  \item \texttt{/status} displays the session configuration and token usage. It is the first place to inspect a session whose settings are unclear.
  \item \texttt{/model} selects the model and reasoning effort. \texttt{/permissions} selects what \name{Codex} may do without asking.
  \item \texttt{/review} asks for a review of changes. A normal request such as ``explain this file'' or ``fix this error'' starts ordinary work.
  \item \texttt{/init} creates a project \name{AGENTS.md}. Our shared adapter already connects this workflow to the existing instructions; running it would introduce another instruction file to maintain.
  \item \texttt{/rename} names the conversation, and \texttt{/resume} reopens a saved chat. The pinned source also includes \texttt{/voice}, whose availability depends on the running client and account.
\end{itemize}

\begin{result}{Starting a session}
The practical starting routine is to enter the project home, launch \name{Codex}, and state the outcome wanted. Existing project notes carry durable progress between conversations. A new chat can read them again; a resumed chat also retains its conversation history.

\end{result}

To return to an existing conversation, I start in the same project home and run \texttt{cxa resume}, which opens a conversation picker filtered to that location. \texttt{cxa resume --last} opens its most recent conversation directly. Inside a running session, \texttt{/resume} opens the picker. The directory is a default filter: \texttt{cxa resume --all} shows conversations from other locations, and \texttt{cxa resume SESSION\_ID} selects a particular conversation by its ID~\cite{codexcli}.

\subsection{Keeping the terminal familiar}

The public \name{codex-ui} repository~\cite{codexui} carries the patch and installer. Its footer follows the public Claude status line and Bash configuration in \name{Unix-dot-files}~\cite{dotfiles}: model, machine, project, context percentage, and consumed five-hour allowance. It also adds double-press quitting and single-line keyboard scrolling.

Each Mac pulls the repository and builds its own executable. The source belongs in \name{\home/Work/GitHub/codex-ui/}. The XDG layout puts the installed program files in \name{\home/.local/share/codex-ui/} and generated build artifacts in \name{\home/.cache/codex-ui/}. The command \name{\home/.local/bin/codex-ui} starts that local installation; the existing \texttt{cxa} alias calls it with our usual permissions. The README gives the installation commands and honours \texttt{XDG\_DATA\_HOME} and \texttt{XDG\_CACHE\_HOME} when set.

\begin{insight}{What a versioned installation contains}
Each release directory contains the patched \name{codex-ui} executable and two helper programs from the same Codex release, \name{codex-code-mode-host} and \name{codex-exec-server}. Together they form one installation. The \name{\lk{current}/} link selects the version to run; \name{\lk{previous}/} selects the version available for rollback. These program files live locally on each Mac. Dropbox carries the shared Codex home described above.
\end{insight}

The pinned Codex release is \texttt{0.166.0}. The current \texttt{update-all} function updates \name{Homebrew} packages, \name{TeX Live}, \name{ble.sh}, and \name{Claude Code}. Updating the custom executable is a separate, manual choice of an upstream release~\cite{codexreleases}. From the packaging repository, replace \texttt{VERSION} with that release number:

\begin{pane}
$ git pull                     # get the published patch and installer changes
$ ./manage.py update VERSION   # build and install the selected Codex release
\end{pane}

The updater fetches the release, applies the patch in a separate checkout, builds it, and selects the new installation once it is complete. If the patch needs porting, the current installation remains available. The installer records a successful update in \name{upstream.json} and the patch; review and commit those together before publishing them for the other Mac. To select the previous installed version:

\begin{pane}
$ ./manage.py rollback   # select the previous local installation
\end{pane}

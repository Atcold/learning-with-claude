\section*{Why we asked}

Today I made pizza dough from a Giallo Zafferano recipe, read off the e-ink tablet: \name{eink}, the site my Mac serves to the tablet, now fetches a recipe and shows it one step per screen. Trader Joe's flour is not the Manitoba and 00 the recipe asks for, so I added 100\,ml of water. Next time I want that note on the ingredients card, next to the 600\,ml it corrects\here[600 ml, or 50 ml for 300]: 100\,ml more for 600\,ml, or 50\,ml if I make 300\,ml.

So \name{eink} has to remember something of mine. Until now it had only code: whatever it knew about me, such as the paths of the PDFs it can show, was written into the program itself. An app that keeps user data needs a place for it, and the question was where. My home folder already says how everyone else answered.

\section{The crowded home folder}

A file or folder whose name starts with a dot is \emph{hidden}: \name{ls} skips it unless asked. That is why programs put their files there, in the home folder, out of sight.

Sixty-seven names, and they are of very different kinds, all in one heap:

\begin{itemize}[leftmargin=1.2em]

\end{itemize}

Two of them are my own tools: \name{.tg-mail} and \name{.chinese-lab}. Each is a link into Dropbox, so that both Macs see the same files. Three names are different: \name{.cache}, \name{.config} and \name{.local}. They are not one program's; they are shared, and they are what this lesson is about.

\section{The convention: four folders, by kind}

\begin{insight}{XDG}
\textbf{XDG} stands for X Desktop Group, the old name of \textbf{freedesktop.org}, where Linux and Unix desktops agree on shared standards. One of them, the \textit{XDG Base Directory Specification} (version 0.8, 8 May 2021), says where a program keeps its files: not in a dot folder of its own, but in one of a few shared folders, chosen by the \emph{kind} of file~\cite{xdg}.
\end{insight}

Each folder has an environment variable that says where it is, and a default for when the variable is not set:

\begin{center}
\begin{tabular}{@{}lll@{}}
  \toprule
  For & Variable & Default \\
  \midrule
  configuration: settings written by hand & \texttt{\$XDG\_CONFIG\_HOME} & \name{\home/.config} \\
  data: what the user would not want to lose & \texttt{\$XDG\_DATA\_HOME} & \name{\home/.local/share} \\
  state: worth keeping across restarts, not precious & \texttt{\$XDG\_STATE\_HOME} & \name{\home/.local/state} \\
  cache: can be thrown away and rebuilt & \texttt{\$XDG\_CACHE\_HOME} & \name{\home/.cache} \\
  \bottomrule
\end{tabular}
\end{center}

Inside each, a program makes one folder named after itself: \name{\home/.config/gh}, \name{\home/.local/share/gh}. State is the newest of the four, added in version 0.8; the specification's examples are logs, history, recently used files, and what to reopen on restart (layout, open files, undo history).

Three rules make the variables safe to use:

\begin{itemize}[leftmargin=1.2em]
  \item a variable that is \emph{not set or empty} means the default;
  \item a variable must hold an \emph{absolute} path, starting with \texttt{/}; a relative one is invalid and is ignored;
  \item the same specification names \name{\home/.local/bin} for the user's own programs, and asks that it be on the \texttt{PATH}. This folder has no variable\here[bin has no variable]: it is always \name{\home/.local/bin}.
\end{itemize}

\needspace{10\baselineskip}
\subsection*{Step 2: are the variables set here?\here[TLCL paragraph cut]}

\begin{pane}
$ echo "config=[$XDG_CONFIG_HOME] data=[$XDG_DATA_HOME] cache=[$XDG_CACHE_HOME] state=[$XDG_STATE_HOME]"
\end{pane}
\begin{cmdout}
|!config=[] data=[] cache=[] state=[]!|
\end{cmdout}

\name{echo} prints its arguments; inside double quotes the shell replaces each \texttt{\$NAME} with that variable's value, and the brackets show where an empty value would be. All four are empty: nothing on my Mac moves them, so every program that follows the convention uses the defaults. That is the usual case, on Linux too.

\subsection*{Step 4: one program, split by kind}

\begin{pane}
$ ls ~/.config/gh ~/.local/share/gh ~/.local/state/gh    # gh's three folders
\end{pane}
\begin{cmdout}
|~/Users/atcold/.config/gh:~|
config.yml  hosts.yml

|~/Users/atcold/.local/share/gh:~|
extensions

|~/Users/atcold/.local/state/gh:~|
extensions  device-id  state.yml
\end{cmdout}

\name{gh}'s settings and the accounts it is logged in to are configuration. The extensions I installed are data: losing them means installing them again. What it noted for itself, such as when it last checked for a new version, is state. One question sorts any file:

\begin{itemize}[leftmargin=1.2em]
  \item Would I edit it by hand? \textbf{Configuration.}
  \item Would losing it lose my work? \textbf{Data.}
  \item Would losing it only lose a convenience? \textbf{State.}
  \item Could the program simply make it again? \textbf{Cache.}
\end{itemize}

\begin{insight}{And Dropbox?}
\here[tg-mail, the eink way]So far \name{.tg-mail} is one folder, linked whole into Dropbox. The question splits it: \name{config.json} is configuration; \name{history} and \name{triage.json} are data; \name{state.json} is state. I am one user with one \name{tg-mail}, and it should behave the same on either Mac: same settings, same data, same state, same cache. With no cloud account to hold them, Dropbox does. The Dropbox folder stays one, \name{Dropbox/dot-tg-mail}, with a subfolder per kind named like the XDG folder it stands for, and each XDG folder gets a link named after the app, as \name{eink} already has:
\begin{itemize}[leftmargin=1.2em]
  \item \name{\home/.config/tg-mail} → \name{Dropbox/dot-tg-mail/config};
  \item \name{\home/.local/share/tg-mail} → \name{Dropbox/dot-tg-mail/share};
  \item \name{\home/.local/state/tg-mail} → \name{Dropbox/dot-tg-mail/state};
  \item \name{\home/.cache/tg-mail} → \name{Dropbox/dot-tg-mail/cache}.
\end{itemize}
Both Macs make the same four links, so both see one app.
\end{insight}

\begin{insight}{And macOS?}
\here[more on macOS]macOS has places of its own for this, in \name{\home/Library}, one per kind: \name{Application Support} for data, where apps with a window keep it (137 folders on my Mac: \name{Anki2}, \name{Firefox}, \name{obsidian}, …); \name{Preferences} for settings, as \name{.plist} files the app writes for me; \name{Caches}, where \name{brew} keeps its downloads; and \name{Logs}. The apps themselves, the programs, are in \name{/Applications}, as \name{.app} bundles. Command-line programs mostly ignore all of these. Many of them run on Linux as well, and following XDG there and on the Mac gives one layout everywhere, the one \name{gh}, \name{nvim} and \name{uv} use above.
\end{insight}

\section{Where \name{brew} keeps things}

\here[new section: brew]XDG says where a program keeps \emph{my} files. Homebrew answers another question: where the programs themselves go. It installs them for the whole Mac, so it copies the layout Unix uses for installed programs (\name{bin}, \name{lib}, \name{share}, \name{etc}, \name{var}) into one folder of its own, its \emph{prefix}. Almost everything is there; the rest goes where macOS wants it.

\subsection*{Step 5: ask \name{brew} where its folders are}

\begin{pane}
$ for w in prefix cellar caskroom cache; do echo "$w: $(brew --$w)"; done
\end{pane}
\begin{cmdout}
prefix: /opt/homebrew
cellar: /opt/homebrew/Cellar
caskroom: /opt/homebrew/Caskroom
cache: /Users/atcold/Library/Caches/Homebrew
\end{cmdout}

\texttt{brew -{}-prefix} and the others print one folder each; the loop labels each line with what was asked. \name{/opt/homebrew} is the prefix on every Mac with an Apple chip (Intel Macs used \name{/usr/local}). Inside it, 21\,GB on this Mac:

\begin{center}
\begin{tabular}{@{}lp{0.62\textwidth}@{}}
  \toprule
  Folder & What it holds \\
  \midrule
  \name{Cellar/} & every \emph{formula}, a command-line program, in a folder per version: \name{Cellar/gh/2.103.2}; 181 here \\
  \name{bin/}, \name{sbin/} & links to the commands, almost all inside \name{Cellar}, 1193 names; this is the folder on the \texttt{PATH} \\
  \name{opt/} & one link per formula to its current version, a path that survives upgrades \\
  \name{lib/}, \name{include/}, \name{share/} & libraries, headers, manuals and data, also links into \name{Cellar} \\
  \name{etc/}, \name{var/} & the installed programs' own settings, logs and running files: real folders, kept across upgrades \\
  \name{Caskroom/} & a record of every \emph{cask}, an app with a window; 35 here \\
  \name{Library/Taps/} & extra sources of formulas and casks I added, such as \name{texstudio-org} \\
  the rest & \name{brew} itself: the prefix is also a git clone of \url{https://github.com/Homebrew/brew}, which \name{brew update} pulls \\
  \bottomrule
\end{tabular}
\end{center}

Outside the prefix, \name{brew} uses the macOS folders:

\begin{itemize}[leftmargin=1.2em]
  \item \name{\home/Library/Caches/Homebrew}: every download, 4.2\,GB here; \name{brew cleanup} empties it;
  \item \name{\home/Library/Logs/Homebrew}: logs of formulas built from source, empty here;
  \item \name{/Applications}: the apps casks install, such as \name{Anki.app};
  \item \name{\home/.homebrew}, the dot folder from Step~1: \name{brew}'s one setting of mine, \name{trust.json}, the third-party taps I trust. \name{brew} would use \name{\home/.config/homebrew} instead, but only when \texttt{\$XDG\_CONFIG\_HOME} is set, and Step~2 showed it is not.
\end{itemize}

\subsection*{Step 6: follow one command to its files}

\begin{pane}
$ readlink /opt/homebrew/bin/gh /opt/homebrew/opt/gh
\end{pane}
\begin{cmdout}
../Cellar/gh/2.103.2/bin/gh
../Cellar/gh/2.103.2
\end{cmdout}

\name{readlink} prints where a link points. \name{gh} is installed once, in \name{Cellar/gh/2.103.2}; \name{bin/gh} is only a link to it. An upgrade puts the new version in a new folder beside it and moves the links; \name{brew cleanup} later deletes the old folder. So \name{gh} the program is in \name{/opt/homebrew}, and \name{gh}'s files about me are in the three XDG folders of Step~4: the two never mix.

\subsection*{Step 7: follow one app}

\begin{pane}
$ readlink /opt/homebrew/Caskroom/anki/*/Anki.app
\end{pane}
\begin{cmdout}
/Applications/Anki.app
\end{cmdout}

A cask is the other way round: the app itself is moved into \name{/Applications}, where the Finder and Spotlight look, and \name{Caskroom} keeps a link to it, to know what to upgrade or remove. Some casks also link a command into \name{bin}: \name{/opt/homebrew/bin/calibre} points into \name{/Applications/calibre.app}.

\subsection*{Step 8: how the shell finds them}

\begin{pane}
$ echo "$PATH" | tr : '\n' | head -3    # the first three folders searched
\end{pane}
\begin{cmdout}
|!/opt/homebrew/bin!|
|!/opt/homebrew/sbin!|
/usr/local/bin
\end{cmdout}

\name{tr} turns the colons between folders into new lines. The shell runs the first match, and \name{brew}'s folders come first: \name{\home/.bashrc} runs \name{brew shellenv}, which puts them there. That is why \name{gh} means \name{/opt/homebrew/bin/gh}, ahead of any older copy the system has.

\section{A home for \name{eink}'s data}

The question sorts \name{eink}'s own files:

\begin{center}
\begin{tabular}{@{}lll@{}}
  \toprule
  What & Kind & Where \\
  \midrule
  the names \name{eink show} knows (\texttt{book}, \texttt{physics}) & configuration & \name{\home/.config/eink/show.toml} \\
  my notes on each recipe & data & \name{\home/.local/share/eink/recipes-notes/}\here[recipes-notes] \\
  \bottomrule
\end{tabular}
\end{center}

The names are written in the program today. Moving them to a file is also a step the project's plan asks for before \name{eink} could ever be released: my paths belong to me, not to the code. The notes are data: I add them from the tablet over time, and losing them loses what I learned at the stove.

In the code, the variable comes first and the default second, with all three rules in two lines: an unset variable reads as empty, and an empty path is not absolute either.

\begin{lstlisting}[style=python]
def data_home():
    """Where eink keeps my data: $XDG_DATA_HOME/eink, or the default."""
    path = os.environ.get("XDG_DATA_HOME", "")
    if not os.path.isabs(path):  # not set, empty, or relative: ignored
        path = os.path.expanduser("~/.local/share")
    return os.path.join(path, "eink")
\end{lstlisting}

Two choices are still open, and they are mine to make:

\begin{enumerate}[leftmargin=1.5em]
  \item \textbf{Strict or loose.} The split above is what the specification means. Many programs simply put everything in \name{\home/.config/eink}; one place is simpler, two places are clearer about what each file is.
  \item \textbf{One Mac or both.} \name{eink} runs on either Mac. \here[both, mirrored]Both, mirroring each other: \name{Dropbox/dot-eink} holds \name{config} and \name{share}, and on each Mac \name{\home/.config/eink} and \name{\home/.local/share/eink} are links to them, so a note added on one is there on the other. When \name{eink} first keeps state or cache, they get a subfolder and a link the same way. The program would not notice: it opens the same path either way.
\end{enumerate}

\section{What this unlocks}

Any service of \name{eink} can now keep what I tell it: first the recipe notes, shown on the ingredients card with a box to add one more; then the names \name{eink show} knows, out of the code. And when my home folder gains a new program, I know where its files should go, and which of my own tools, \name{.tg-mail} and \name{.chinese-lab}, still live by the old habit. \here[other projects next]They are next: each moves to the same split, every kind in its XDG folder, each linked into Dropbox.

\section*{Why we asked}

The Chinese practice app will run in the phone's browser, served from \name{cims}. When I mismatch two words, say \yuanyi\ \textit{\toneD{yuàn}\toneD{yì}} ‘willing’ with \yuanyin\ \textit{\toneB{yuán}\toneA{yīn}} ‘reason’, the app should record the mistake somewhere Claude can later read and copy into the vault. The question was whether \name{cims} can do that on its own.

\section{The starting point: a file server}

My web space on \name{cims} is the folder \texttt{public\_html} in my home directory there. Whatever file I put in it, the web server (\name{Apache}) hands out to anyone who asks for its address. That is how the dictionary is published: \name{deploy.py} copies the files there with \texttt{scp}, and the phone fetches them.

\end{tikzpicture}
\end{center}

This road is one-way. The web can only \emph{read} files. Only someone logged in to \name{cims}, me or Claude over \texttt{ssh}, can change them.

\section{What a mistake log needs: a POST, and something to catch it}

To save a mistake, data has to travel the other way, from the phone to \name{cims}. Browsers can send data: that request is called a \textbf{POST}. But a plain file cannot receive anything. Something on \name{cims} has to take the POST and write it down, and that something has to be a \textbf{program} the server runs when the request arrives.

\begin{insight}{CGI}
The old, simple way for \name{Apache} to run a program is \textbf{CGI} (Common Gateway Interface). The rules are short. A file whose name ends in \texttt{.cgi} and that is allowed to execute gets \emph{run} instead of sent. Whatever the program prints is what the browser receives. It must print a header line saying what kind of content follows, then one empty line, then the content.
\end{insight}

Whether \name{Apache} on \name{cims} is allowed to run \emph{my} programs is a setting NYU chooses, and I cannot see it from outside. So we tried it.

\section{The test}

The probe is the smallest CGI program possible. It prints the header, the empty line, and the word \texttt{hello}:

\begin{script}
#!/usr/bin/env python3
print("Content-Type: text/plain")
print()
print("hello")
\end{script}

The first line tells the system which interpreter runs the file (\name{Python}~3). \texttt{text/plain} says the content is plain text. The bare \texttt{print()} is the empty line that ends the headers.

\subsection*{Step 1: look at the script}

\begin{pane}
cd ~/Work/Scratch && clear && cat probe.cgi
\end{pane}

\texttt{clear} wiped the pane \emph{before} \texttt{cat} printed the script, so the script was on screen afterwards. The commands typed before it were what got erased.

\subsection*{Step 2: upload it and make it executable}

\begin{pane}
scp probe.cgi cims:public_html/ && ssh cims 'chmod 755 public_html/probe.cgi' && echo uploaded
\end{pane}
\begin{cmdout}
probe.cgi                                       100%   80     6.8KB/s   00:00
uploaded
\end{cmdout}

\texttt{scp} copies the file into \texttt{public\_html}. \texttt{chmod 755} sets its permissions: I may read, write and run it, everyone else may read and run it. Without the ‘run’ bit, \name{Apache} would refuse to execute it. \texttt{\&\&} runs the next command only if the previous one succeeded, so \texttt{uploaded} appears only if both worked.

\subsection*{Step 3: ask for it, as a browser would}

\begin{pane}
curl -si https://cims.nyu.edu/~atcold/probe.cgi | head -15
\end{pane}
\begin{cmdout}
|!HTTP/2 200!|
|!content-type: text/plain; charset=UTF-8!|
|~date: Sat, 17 Oct 2026 16:42:47 GMT~|
|~server: Apache/2.4.62~|
|~content-security-policy: upgrade-insecure-requests~|
|~strict-transport-security: max-age=31536000; preload;~|
|~set-cookie: USERSERVERID=p1; path=/~|
|!hello!|
\end{cmdout}

\texttt{curl} fetches an address from the terminal: \texttt{-s} keeps it silent about progress, \texttt{-i} also shows the response headers, the lines before the content. \texttt{head -15} keeps only the first 15 lines.

\begin{result}{\name{cims} runs my programs}
The answer is \texttt{hello}, and the content type is the \texttt{text/plain} the script printed. So \name{Apache} \emph{ran} the script and sent back its output. Had it only served files, the answer would have been the script's own text, the four \name{Python} lines, or an error page. \texttt{200} is HTTP for ‘OK’.
\end{result}

\subsection*{Step 4: remove the probe}

\begin{pane}
ssh cims 'rm public_html/probe.cgi' && curl -s -o /dev/null -w '%{http_code}\n' https://cims.nyu.edu/~atcold/probe.cgi && rm probe.cgi
\end{pane}
\begin{cmdout}
|!403!|
\end{cmdout}

This deletes the script on \name{cims}, asks for its address again, and deletes the local copy. This time \texttt{curl} throws the content away (\texttt{-o /dev/null}) and prints only the status code (\texttt{-w}). \texttt{403} means the server refuses: the probe is no longer answering. We did not check what that address returned \emph{before} the upload, so this lesson cannot say why \name{cims} answers 403 here rather than 404 (‘not found’).

\section{What this unlocks}

The phone can now POST each mistake to a small program on \name{cims}, which appends it to a file. Claude then copies the new lines into the vault over \texttt{ssh}. Two precautions come with it:

\begin{itemize}[leftmargin=1.2em]
  \item The program answers anyone who finds its address, so the app sends a secret word with every POST, and the program ignores any request without it.
  \item The mistakes file lives outside \texttt{public\_html}, so the web can write to it only through the program, and never read it back.
\end{itemize}

\section*{Why we asked}

\here[the app, defined] I am building a Chinese practice app: a web page where I match characters, sounds and meanings by drawing lines between them. It will run in the phone's browser, served from \name{cims}. When I mismatch two words, say \yuanyi\ \textit{\toneD{yuàn}\toneD{yì}} ‘willing’ with \yuanyin\ \textit{\toneB{yuán}\toneA{yīn}} ‘reason’, the app should record the mistake somewhere Claude can later read and copy into the vault. The question was whether \name{cims} can do that on its own.

\section{The starting point: a file server}

My web space on \name{cims} is the folder \name{public\_html} in my home directory there. Whatever file I put in it, the web server (\name{Apache}) hands out to anyone who asks for its address. \here[HTTP, defined] Browser and server talk in \textbf{HTTP} (HyperText Transfer Protocol). Each exchange is a request (a method, an address, a few header lines) and a response (a status code such as \texttt{200}, ‘OK’, header lines, then the content)~\cite[p.~994]{lutz}.\here[cited: Lutz p.~994] The request ‘give me this file’ uses the method \texttt{GET}. That is how the dictionary is published: \name{deploy.py} copies the files there with \name{scp}, and the phone fetches them.

This road is one-way. The web can only \emph{read} files. Only someone logged in to \name{cims}, me or Claude over \name{ssh}, can change them.

\section{What a mistake log needs: a \texttt{POST}, and something to catch it}

To save a mistake, data has to travel the other way, from the phone to \name{cims}. Browsers can send data: that request is called a \texttt{POST}. But a plain file cannot receive anything. Something on \name{cims} has to take the \texttt{POST} and write it down, and that something has to be a \textbf{program} the server runs when the request arrives.

\end{tikzpicture}

\begin{insight}{CGI}
The old, simple way for \name{Apache} to run a program is \textbf{CGI} (Common Gateway Interface)~\cite[p.~1126]{lutz}.\here[cited: Lutz p.~1126] The rules are short. A file whose name ends in \texttt{.cgi} and that is allowed to execute gets \emph{run} instead of sent. Whatever the program prints is what the browser receives. It must print a header line saying what kind of content follows, then one empty line, then the content.
\end{insight}

Whether \name{Apache} on \name{cims} is allowed to run \emph{my} programs is a setting NYU chooses, and I cannot see it from outside. So we tried it.

\section{The test}

The probe is the smallest CGI program possible. It prints the header, the empty line, and the word \texttt{hello}:

\begin{script}
#!/usr/bin/env python3
print("Content-Type: text/plain")
print()
print("hello")
\end{script}

The first line tells the system which interpreter runs the file (\name{Python}~3). \texttt{text/plain} says the content is plain text. The bare \texttt{print()} is the empty line that ends the headers.

\subsection*{Step 1: look at the script}

\begin{pane}
$ cd ~/Work/Scratch    # where probe.cgi was written
$ cat probe.cgi        # print it, to see what goes up
\end{pane}

\subsection*{Step 2: upload it and make it executable}

\begin{pane}
$ scp probe.cgi cims:public_html/ &&             # copy it into the web folder
  ssh cims 'chmod 755 public_html/probe.cgi' &&  # make it runnable
  echo uploaded                                  # reached only if both worked
\end{pane}
\begin{cmdout}
probe.cgi                                       100%   80     6.8KB/s   00:00
uploaded
\end{cmdout}

\here[\texttt{\$} prompt; comments in Steps 1, 2, 4; prose trimmed] \texttt{chmod 755} sets the file's permissions: I may read, write and run it, everyone else may read and run it. Without the ‘run’ bit, \name{Apache} would refuse to execute it. \texttt{\&\&} runs the next command only if the previous one succeeded, and a line ending in it continues on the next, which leaves room for a comment after each step: the shell ignores everything from \texttt{\#} to the end of the line.

\subsection*{Step 3: ask for it, as a browser would}

\begin{pane}
$ curl -si https://cims.nyu.edu/~atcold/probe.cgi | head -15
\end{pane}
\begin{cmdout}
|!HTTP/2 200!|
|!content-type: text/plain; charset=UTF-8!|
|~date: Sat, 17 Oct 2026 16:42:47 GMT~|
|~server: Apache/2.4.62~|
|~content-security-policy: upgrade-insecure-requests~|
|~strict-transport-security: max-age=31536000; preload;~|
|~set-cookie: USERSERVERID=p1; path=/~|
|!hello!|
\end{cmdout}

\name{curl} fetches an address from the terminal: \texttt{-s} keeps it silent about progress, \texttt{-i} also shows the response headers, the lines before the content. \texttt{head -15} keeps only the first 15 lines.

\begin{result}{\name{cims} runs my programs}
The answer is \texttt{hello}, and the content type is the \texttt{text/plain} the script printed. So \name{Apache} \emph{ran} the script and sent back its output. Had it only served files, the answer would have been the script's own text, the four \name{Python} lines, or an error page. \texttt{200} is HTTP for ‘OK’.
\end{result}

\subsection*{Step 4: remove the probe}

\begin{pane}
$ ssh cims 'rm public_html/probe.cgi' &&         # delete it on cims
  curl -s -o /dev/null -w '%{http_code}\n' \
    https://cims.nyu.edu/~atcold/probe.cgi &&    # ask again, keep only the status
  rm probe.cgi                                   # delete the local copy
\end{pane}
\begin{cmdout}
|!403!|
\end{cmdout}

\here[prose trimmed; \texttt{-w} explained] \texttt{-o /dev/null} throws the content away. \texttt{-w} takes a format to print once the request is done: \name{curl} replaces \texttt{\%\{http\_code\}} with the status code, and \texttt{\textbackslash n} ends the line. The single quotes stop the shell from touching the \texttt{\%} and the \texttt{\textbackslash}~\cite{curl}. \texttt{403} means the server refuses: the probe is no longer answering. We did not check what that address returned \emph{before} the upload, so this lesson cannot say why \name{cims} answers 403 here rather than 404 (‘not found’).

\section{What this unlocks}

The phone can now \texttt{POST} each mistake to a small program on \name{cims}, \name{log.cgi}, which appends it to a file. Claude then copies the new lines into the vault over \name{ssh}.

\here[new: a POST, step by step] A mistake travels like this~\cite[pp.~1128--1129]{lutz}:

\begin{enumerate}[leftmargin=1.5em]
  \item The phone's browser sends a \texttt{POST} to the address of \name{log.cgi}, with the mistake in the body of the request. The practice app's code tells it to.
  \item \name{Apache} on \name{cims} sees a \texttt{.cgi} file at that address and runs it, instead of sending it.
  \item \name{log.cgi} reads the body of the \texttt{POST} on its standard input, as if it were typed at it. Details such as its length arrive as environment variables.
  \item What it does next is up to us: it is our program. Here, it checks who sent the mistake, then appends a line to the mistakes file.
  \item Whatever it prints goes back to the phone as the response, as \texttt{hello} did in the test. That is how the app learns whether the mistake was saved or refused.
\end{enumerate}

\name{log.cgi} answers anyone who finds its address, so it has to tell my mistakes from anyone else's:

\begin{itemize}[leftmargin=1.2em]
  \item Nothing secret can live in the \here[‘practice’ added] practice app: every browser that opens it downloads its code, and anyone can read it. So the app asks me who I am the first time it sends a mistake, keeps the answer on the phone, and sends it with every \texttt{POST}. \here[identity editable] I can change the answer there if I mistype it.
  \item \name{log.cgi} appends only my mistakes and refuses the rest; the app shows a notice when a \texttt{POST} is refused. Its code is never sent out, and holds nothing personal anyway: it reads a small config file on \name{cims}, outside \name{public\_html}, with a hash of my user (a fingerprint that can be checked but not turned back into the user) and the place of the mistakes file. \name{deploy.py} writes that file from my own config.
  \item The mistakes file also lives outside \name{public\_html}, so the web can write to it only through \name{log.cgi}, and never read it back.
\end{itemize}
